# 记忆深度整理系统(v2.1)设计文档

## 一、背景与问题定义

当前记忆系统已实现四层结构(回合小结 → 章节 → 卷 → 事实库)与五路检索,解决了"旧剧情被遗忘"的问题。但长局(100+ 回合)中出现了另一类退化:**记忆积压导致的 AI 降智**。其成因不是信息缺失,而是信息污染:

1. **事实重复**:同一事件被主模型、二次模型、任务系统以不同措辞记录多次,`facts` 90 行中有效信息可能不足一半;
2. **NPC 笔记碎片化**:每 NPC 5 条孤立记录,缺乏"关系走向"的连贯叙述,AI 需要自行拼凑;
3. **僵尸线索**:已解决的线索仍以"未解"状态占据注入预算;
4. **摘要漂移**:机械截断产生的早期摘要与后期 AI 摘要可能相互矛盾,AI 无所适从。

注入的记忆越多、矛盾越多,主模型越倾向于输出保守、模板化、重复确认的叙事——这就是"降智"的直接机理。

## 二、方案总览

引入**深度整理(Deep Consolidation)**机制:每 36 回合(可配置),将过去一个周期内积累的全部动态记忆交给主模型做一次"清洗式压缩",输出结构化 JSON 后确定性写回。与现有机制的分工:

| 机制 | 周期 | 模型 | 职责 |
|---|---|---|---|
| 章节固化 | ~10 回合 | 二次模型 | 细粒度剧情摘要(叙事保真) |
| 卷固化 | ~100 回合 | 二次模型 | 粗粒度主线脉络 |
| **深度整理** | **36 回合** | **主模型** | **全库清洗:去重、合并、矛盾消解、线索结算** |

深度整理不新增记忆层,而是原位重写现有层,记忆总量在整理后**下降**而非上升。

## 三、新增/修改模块清单

| 模块 | 类型 | 职责 |
|---|---|---|
| `js/data/memory-config.js` | 新增 | 记忆参数默认值、localStorage 持久化(`naruto_memory_config`)、`getMemoryConfig()/saveMemoryConfig()` |
| `js/systems/memory-system.js` | 修改 | 新增 `deepConsolidate(client)`(整理主流程)、`shouldDeepConsolidate()`(周期判定)、`getMemoryStats()`(体积统计);既有窗口常量改读配置 |
| `js/core/pipeline.js` | 修改 | 回合完成钩子:`shouldDeepConsolidate()` 为真时,按配置选主模型或二次模型客户端,fire-and-forget 调用 `deepConsolidate` |
| `js/ui/memory-panel.js` | 新增 | 设置内"记忆"板块 Web Component:参数表单 + 记忆浏览器 + 手动操作 |
| `js/ui/settings-panel.js` | 修改 | 挂载记忆板块入口 Tab |

## 四、深度整理数据流

1. **触发**:回合 N 完成且 `N - meta.last_deep_turn >= cycle`(默认 36)。`last_deep_turn` 持久化在 `memory.meta`,读档/刷新不重复触发;
2. **取材**:打包周期内的 `facts` 全量、`npc_notes` 全量、`clues` 全量、`pins`、本周期章节摘要、`important_events`(总量截断至 12000 字符);
3. **调用**:temperature 0.2,max_tokens 3000,严格 JSON 输出协议(见第五节);
4. **校验**:花括号配对提取 JSON → 结构校验(字段类型、数量上限)→ `updated_at` 版本防护(整理期间玩家已开新回合则放弃,下周期重试);
5. **写回**:`facts` 整体替换为去重合并版、`npc_notes` 替换为"关系简史+近况"、`clues` 中 status=已解 的移入 `important_events`、`pins` 采纳精简建议;写回后 `last_deep_turn = N`;
6. **降级**:任何一步失败即无操作退出——旧数据完整保留,绝不让坏输出污染记忆库。

## 五、整理提示词设计原则(严谨性保障)

系统提示词核心约束(全文见实现):

- **零虚构**:「你只能重组、合并、删减既有条目,严禁添加输入中不存在的任何事实、人名、数值」;
- **保留回合锚点**:合并事实时保留最早出现的 `#回合号`,时间线可回溯;
- **矛盾处理规则**:「两条记录冲突时,保留回合号更大者,并在该条目附注 (曾记载:...)」——矛盾显式化而非静默丢弃;
- **配额硬限制**:facts ≤40 条、每 NPC 简史 ≤80 字+近况 ≤40 字、结算线索需给出结算依据;
- **输出协议**:仅输出一个 JSON 对象,字段为 `facts[]`、`npc_digest{}`、`resolved_clues[]`、`pins[]`、`era_note`,任何解释性文字都会导致解析失败被丢弃(这一点写明,让模型自律)。

## 六、设置面板「记忆」板块

**参数区**(写入 memory-config):
- 深度整理:开关 / 周期(12–100,默认 36)/ 使用模型(主模型|二次模型);
- 分层参数:章节窗口(默认 10)、回合小结上限(8)、注入总预算(7200 字)、facts 上限(90)、归档上限(600);
- 检索:`<recall>` 协议开关、召回有效期(默认 3 回合)。

**浏览与管理区**:
- 分层体积统计条(各层字符数/条数,直观看到积压);
- 章节/卷列表:标题+回合区间+摘要,支持行内编辑与删除;
- pins/facts 检索式浏览,支持删除与"提升为置顶";
- 操作按钮:「立即深度整理」(手动触发,带确认)、「导出记忆 JSON」/「导入」、「清空待归章缓冲」。

**安全设计**:所有编辑经 `memorySystem` 写入(带 `_stateVersion` 递增),不直改 state;删除操作二次确认;导入做结构校验。

## 七、实施步骤

1. `memory-config.js` + memory-system 常量配置化(半天);
2. `deepConsolidate` 主流程 + 提示词 + JSON 校验写回(1 天);
3. pipeline 触发钩子 + 版本防护联调(半天);
4. `memory-panel.js` UI(1–1.5 天);
5. 长局回归测试:模拟 40+ 回合验证触发、断网降级、读档不重触发(半天)。

## 八、验收标准

- 36 回合整理后 `facts` 条数下降 ≥40%,无新增虚构条目(抽查比对);
- 整理期间玩家正常游戏不受阻塞,失败时记忆库与整理前逐字节一致;
- 读档/刷新后 `last_deep_turn` 生效,不重复整理;
- 设置面板参数修改即时生效并在刷新后保留;
- 手动"立即整理"与自动触发走同一代码路径。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 主模型输出非法 JSON | 花括号提取+结构校验,失败零写入 |
| 整理与新回合并发竞争 | `updated_at` 版本防护(已有成熟模式) |
| 整理丢失关键细节 | 保守配额(40 条 facts 而非 20)+ 矛盾附注机制 + 原文仍存于章节 raw/时间线节点,可回溯 |
| 主模型调用成本 | 每 36 回合一次,输入 ≤12k 字符;可在设置中切换为二次模型 |
