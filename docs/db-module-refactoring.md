# 项目代码优化与更新技术文档 — 文件型数据库模块（`server/db/index.js`）

> 重构范围：`server/db/index.js`（232 行 → 约 330 行，含完整 JSDoc 类型标注）
> 对外 API：**14 个导出函数的签名、同步语义、返回值 100% 保持不变**，全部调用方（`server/api/saves.js`、`server/api/music-favorites.js`、`server/middleware/auth.js`、`server/auth/discord.js`、`server/index.js`）**零改动**。

---

## 1. 重构摘要 (Executive Summary)

本次重构在不改变任何对外契约的前提下，消除了文件型数据库模块中**阻塞事件循环的自旋锁**与**静默清空全量数据**两个生产级缺陷，并通过「内存写穿缓存 + 原子写落盘」将读操作从每次 O(文件体积) 的磁盘读降为 O(1) 缓存访问——实测综合读吞吐提升约 **9 倍**（300 用户 / 500 存档规模下，2000 轮混合读操作 3835ms → 414ms），且数据规模越大收益越大。

## 2. 痛点与缺陷诊断 (Code Smell Analysis)

| # | 缺陷 | 专业定性 | 后果 |
|---|------|----------|------|
| 1 | `while (Date.now() - start < 50) {}` 重试等待 | **忙等待自旋锁（Busy-wait Spin Lock）阻塞事件循环** | 读文件失败时每次重试空转烧 CPU 50ms，最多 5 次 = **整个 Node 进程冻结 250ms**（实测 252ms），期间所有并发 HTTP 请求全部停摆。这是单线程运行时的大忌 |
| 2 | `fs.writeFileSync(filePath, ...)` 直写目标文件 | **非原子写（Torn Write）** | 进程在写入中途崩溃 / 被 kill，磁盘上留下半截或空文件。缺陷 1 的重试逻辑正是为这个自己制造的问题打的补丁——**治标不治本的循环依赖** |
| 3 | 读失败 5 次后 `return defaultVal` | **错误吞噬（Error Swallowing）导致静默数据清空** | 若 `users.json` 损坏，读操作返回 `{}`；随后任意一次 `upsertUser` 会把这个空对象**原样写回磁盘**——全部用户数据无声蒸发，且无任何现场可供恢复（已在隔离环境实测复现） |
| 4 | 每个操作都 `readFileSync + JSON.parse` 整个文件 | **重复 I/O，O(文件体积) 时间复杂度** | `getUserSaveCount` 这种只需要一个数字的调用也要完整解析几百 KB 的索引文件，产生大量瞬时对象加剧 GC 压力 |
| 5 | 写失败仅 `console.error` 后继续 | **失败静默（Fail-Silent）** | `upsertUser` / `saveUserFavorites` 落盘失败时上层路由照常返回成功，用户以为已保存，实际数据已丢 |
| 6 | `song.url_id \|\| song.mid \|\| song.id` 在 3 处重复 | **DRY 违例** | 歌曲主键规则一旦调整需同步改 3 处，极易漏改 |
| 7 | 收藏上限 `100` 以字面量散落两处 | **魔法数字（Magic Number）** | 语义不明，两处还语义相反（见 §6 疑问 1） |
| 8 | `if (!fs.existsSync(dbDir))` 判断模块自身所在目录 | **死代码（Dead Code）** | `dbDir` 即模块自身目录，模块能被加载则目录必然存在，恒为 false |
| 9 | 返回值直接暴露解析出的对象引用 | 弱**封装泄漏**风险 | 旧实现靠「每次重新读盘」侥幸避免缓存污染；一旦有人加缓存而不加防御性拷贝，调用方的就地修改会直接腐蚀数据源 |
| 10 | 全模块无任何类型标注 | **缺乏类型契约** | `SaveMetadata`、`Song` 等结构只能靠通读调用方源码反推 |

## 3. 架构与模式升级 (Architecture & Pattern Updates)

```
┌────────────────────────────────────────────────┐
│  导出的仓储函数（Repository，业务规则所在层）      │
│  upsertUser / getUserSaves / addUserFavorite …  │
├────────────────────────────────────────────────┤
│  JsonStore（每个 JSON 文件一个实例）             │
│  懒加载 → 内存缓存 → save() 原子落盘             │
├────────────────────────────────────────────────┤
│  atomicWriteFileSync（temp file + rename）      │
└────────────────────────────────────────────────┘
```

1. **仓储模式（Repository Pattern）+ 单一职责拆分**：新增 `JsonStore` 类，只负责「加载 / 缓存 / 原子落盘」单个 JSON 文件，对文件内容的业务含义零感知；用户、存档索引、收藏各持有一个实例。业务规则（去重、上限、时间戳维护）全部留在导出的仓储函数层。原先「读文件 → 改 → 写文件」的样板代码从每个函数中消失。
2. **写穿缓存（Write-through Cache）**：JSON 文件首次访问时加载进内存，读操作直接命中缓存，写操作先改缓存再同步落盘。成立前提是**本进程是数据文件的唯一写入者**——已核查整个仓库（含部署脚本），确认无第二写入者，并在模块头注释中将该前提显式声明为架构约束。
3. **原子写（Atomic Write / Write-Rename Pattern）**：所有落盘（含 `saves/*.bin` 二进制存档）改为「写同目录临时文件 → `rename` 覆盖」。`rename` 在同一文件系统内是原子操作，任何读取方要么看到旧的完整内容、要么看到新的完整内容——**从根源上消灭了"文件暂时为空"这一自旋锁存在的理由**，缺陷 1、2 被同一个机制一并解决。
4. **损坏隔离（Quarantine Pattern）**：JSON 解析失败时不再静默返回默认值，而是把损坏文件改名为 `*.corrupt-<时间戳>` 保留现场、记录错误日志后以空数据继续服务——可用性行为与旧版一致（服务不中断），但数据可人工修复找回，堵死缺陷 3 的静默清空路径。
5. **快速失败（Fail-Fast）**：`JsonStore.save()` 落盘失败时向上抛出异常，由既有路由层的 `try/catch` 统一转为 HTTP 500。持久化失败不再伪装成功（详见 §6 行为变更说明）。
6. **防御性拷贝（Defensive Copy）**：所有读接口经 `structuredClone` 返回深拷贝，与旧版「每次读盘得到全新对象」的语义完全一致，同时保证缓存永不被调用方污染（已列入 parity 测试断言）。
7. **刻意不做的设计**（KISS，防过度设计）：不引入依赖注入容器、不抽象 `IDatabase` 接口、不新增任何 npm 依赖、不把同步 API 改为异步。对外同步契约被 4 个调用方直接依赖，改异步属于破坏性重构；若未来需要多进程部署，正确路径是整体替换为 SQLite 而非在本模块上继续叠加文件锁（已写入模块头注释）。

## 4. 性能与复杂度对比 (Performance & Complexity Metrics)

| 指标 | 重构前 | 重构后 |
|------|--------|--------|
| 单次读操作时间复杂度 | O(F)（F=文件字节数，读盘 + 全量 `JSON.parse`） | **摊还 O(1)**（首次访问 O(F)，之后命中内存缓存）；`getUserSaves` 等遍历型仍为 O(记录数)，但不再有 I/O |
| 读失败最坏阻塞 | **252ms 事件循环冻结**（实测，5×50ms 自旋） | 2ms（实测，无自旋路径） |
| 综合读吞吐（300 用户 / 500 存档，2000 轮 `getUser`+`getUserSaves`+`getUserSaveCount`） | 3835ms（1918µs/轮） | **414ms（207µs/轮），约 9.3×** |
| 单次写操作 | O(F) 序列化 + 1 次写 | O(F) 序列化 + 1 次写 + 1 次 rename（rename 为常数级元数据操作，可忽略） |
| 空间 | 每次调用产生 O(F) 瞬时对象，GC 高频回收 | 每文件常驻 O(F) 缓存（当前数据量为 KB 级，代价可忽略），瞬时分配仅剩返回值深拷贝 |
| 崩溃一致性 | 可能留下半截/空文件 | 任意时刻崩溃，磁盘上均为完整旧版或完整新版 |

## 5. 依赖与语法更新 (Dependency & Syntax Migration)

**零新增 npm 依赖**，仅使用 Node.js ≥ 18 内建能力（项目实际运行于 Node 24）：

| 旧写法 | 新写法 | 说明 |
|--------|--------|------|
| `import fs from 'fs'` | `import fs from 'node:fs'` | `node:` 协议前缀，显式区分内建模块与三方包，Node 官方推荐写法 |
| 手写 5 次重试 + 自旋等待 | `atomicWriteFileSync`（temp + `renameSync`） | 用正确的写入机制取代对错误写入机制的补偿 |
| 无封装的自由函数 + 模块级可变状态 | `class JsonStore` + **私有类字段 `#cache`**（ES2022） | 缓存对模块外不可见，杜绝旁路篡改 |
| 返回内部对象引用 | **`structuredClone`**（Node 17+） | 原生深拷贝，替代 `JSON.parse(JSON.stringify())` 惯用法 |
| `if (fs.existsSync(p)) fs.unlinkSync(p)` | `fs.rmSync(p, { force: true })`（Node 14.14+） | 消除 check-then-act 竞态窗口，语义即"存在则删" |
| `if (!fs.existsSync(savesDir)) fs.mkdirSync(...)` | `fs.mkdirSync(savesDir, { recursive: true })` | `recursive` 模式天然幂等，无需前置判断 |
| 无类型信息 | JSDoc `@typedef`（`UserRecord` / `SaveMetadata` / `SaveRecord` / `Song` 等） | 无需引入 TypeScript 构建链即可获得 IDE 补全与 `tsc --checkJs` 兼容的类型契约，符合项目"无构建步骤"的现状 |
| 字面量 `100` ×2 | `MAX_FAVORITES_PER_USER` 命名常量 | 消除魔法数字 |
| `song.url_id \|\| song.mid \|\| song.id` ×3 | `getSongKey(song)` | DRY |

## 6. 边界测试与防坑指南 (Edge Cases & Fallbacks)

### 6.1 验证方法

- **行为等价性测试（Parity Harness）**：同一份含 40+ 断言点的操作剧本分别驱动旧模块与新模块（各自隔离数据目录），对比三个观测面——stdout 返回值、stderr 日志、最终磁盘文件内容。结果：**除时间戳墙钟差异外逐字节一致**。
- **端到端冒烟**：以 `AUTH_BYPASS=true` 启动真实服务，走通 `POST/GET/PUT/DELETE /api/saves`（含 gzip 压缩存档往返）与 `/api/music` 收藏增删改查全链路。

### 6.2 已逐一保全的边界契约（防疏漏清单）

| 边界场景 | 保持的行为 |
|----------|-----------|
| JSON 文件不存在 / 内容为空 | 返回默认空结构，服务不中断 |
| `getUser` 未命中 | 返回 `null`（而非 `undefined`） |
| `upsertUser` 已存在用户 | 保留 `created_at`，仅刷新资料与 `last_login` |
| `getSaveById`：索引存在但 `.bin` 缺失（孤儿索引） | 返回 `null`，与"索引不存在"不可区分（调用方依赖此归一化），且不刷错误日志 |
| `updateSave` 目标不存在 | 静默 no-op（路由层已先校验归属，此处是第二道防线） |
| `updateSave` 仅传部分字段 | 只覆盖显式非 `undefined` 的字段；传 `save_data` 而不传 `size_bytes` 时 `size_bytes` 随之置空——旧版怪异行为，**原样保留** |
| `deleteSave` 先删索引后删 `.bin`，`.bin` 删除失败仅记日志 | 保留：索引已删则对外不可见，残留孤儿文件不影响正确性，不让用户的删除操作报错回滚 |
| `saveUserFavorites` 传非数组 | 静默忽略、不落盘 |
| `removeUserFavorite` 对不存在的用户 | 返回 `[]` 并为该用户建空列表落盘（旧版如此，保留） |
| `getUserSaves` 排序 | 仍按 `new Date(updated_at)` 数值倒序（对非法日期的容错行为与旧版一致） |
| 收藏上限 | `addUserFavorite` 超限保留**最后** 100 首；`saveUserFavorites` 超限保留**前** 100 首（见疑问 1） |

### 6.3 明确的行为变更（有意为之，非疏漏）

1. **JSON 落盘失败由静默改为抛出** → 既有路由 `try/catch` 转为 HTTP 500。旧行为是"告诉用户保存成功但其实丢了"，属于缺陷而非特性，故修正并在此声明。
2. **损坏文件由静默丢弃改为隔离保留**（`*.corrupt-<时间戳>`），对外可观测行为（返回默认值、服务继续）不变。
3. **孤儿索引不再产生日志**：旧版对"`.bin` 不存在"静默、对"读取报错"记日志；新版统一为仅对非 `ENOENT` 的 I/O 错误记日志。

### 6.4 留给原作者的疑问（不确定是否为特意设计，未擅自"修复"）

1. **两处收藏截断方向相反**：`addUserFavorite` 用 `slice(-100)`（挤掉最旧的），`saveUserFavorites` 用 `slice(0, 100)`（丢弃末尾多余的）。前者像 LRU 语义，后者像"信任客户端排序"。已原样保留并以注释标明，**建议确认是否应统一**。
2. **`getDb()` 恒返回 `true`**：疑为早期对接真数据库的占位句柄。仓库内已无调用方，但作为公共导出可能被外部依赖，故保留并注明"历史遗留"。

### 6.5 后续维护防坑事项

- **单进程假设是本模块的生命线**：内存缓存的正确性建立在"本进程是唯一写入者"之上。上 PM2 cluster、多实例、或任何第二个进程写这些 JSON 文件之前，必须整体迁移到真数据库（模块头注释已声明）。
- **不要在运行期手改 `server/db/*.json`**：旧版每次读盘、能"看见"手工修改；新版缓存后**需重启进程才生效**。
- **不要把 `JsonStore#data` 的引用泄漏出模块**：所有新增读接口必须过 `structuredClone`，否则调用方的就地修改会腐蚀缓存并在下次 `save()` 时落盘。
- **`*.tmp` / `*.corrupt-*` 文件**：`.tmp` 是原子写的瞬时中间态（崩溃残留可安全删除）；`.corrupt-*` 是待人工修复的数据现场，清理前请先确认无需恢复。
- **同步 I/O 是契约不是疏忽**：4 个调用方以同步方式调用本模块。若要异步化，必须同时改造全部调用方并评估路由层错误处理，属于独立的破坏性重构。
